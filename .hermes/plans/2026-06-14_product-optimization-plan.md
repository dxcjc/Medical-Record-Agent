# Medical Record Agent — 产品化规划文档（合并版）

> **版本**: v3.0（合并体验缺陷 + 功能缺失 + 产品视角深度分析）
> **日期**: 2026-06-14
> **范围**: 全系统前端 + 后端 + 用户体验 + 功能完整性
> **优先级**: P0=体验阻断 → P1=功能缺失 → P2=体验粗糙 → P3=锦上添花

---

## 一、产品定位与现状

### 产品定位
Medical Record Agent 是一个**医学检验报告智能识别系统**，核心用户流程：

```
上传报告 → OCR+LLM 识别 → 人工复核 → 知识库沉淀 → 回写目标系统
```

### 现状评估
系统完成了"能跑通"的 MVP 阶段，但**每个环节都有断点**：

| 环节 | 完成度 | 断点 |
|------|--------|------|
| 上传识别 | ✅ 90% | 基本可用，置信度计算有 bug |
| 人工复核 | ✅ 85% | 字段详情展示、OCR 定位可用，但反馈提交后"石沉大海" |
| 知识库管理 | 🟡 60% | 能看不能改，反馈无法写入知识库 |
| 评测质量 | 🟡 40% | 框架在，但样本导入门槛高，非技术人员用不了 |
| 回写下游 | 🔴 20% | 手动触发不可用，只展示历史 |
| Provider 管理 | 🟡 50% | 能看状态，不能增删改 |
| Schema 管理 | 🟡 50% | 能看版本，不能新建编辑 |
| 统计分析 | 🔴 30% | Dashboard 只有 4 个数字，趋势图/字段统计 API 404 |
| 审计追踪 | 🟡 40% | 有日志但无筛选导出 |
| 系统体验 | 🔴 30% | 按钮静默失败、刷新丢登录、白屏无兜底 |

**一句话总结**：系统"能用"但"不好用"——每个功能都有入口，但一半的按钮点了没反应或没有下一步。

## 二、系统性根因分析

### 根因 1：缺少"体验中间层"（架构缺陷）

当前架构：
```
API Client → 各页面自行 catch 错误 → 各自展示（有的 toast、有的静默、有的白屏）
```

应有的架构：
```
API Client → 全局错误拦截 → 统一消息提示 + Loading 状态 + 网络检测 + 401 去重
```

**具体表现**：
- 5 个按钮 POST/DELETE 无 body → Fastify 400 → catch 里只显示"操作失败" → 用户以为没点上
- 无 React Error Boundary → 渲染报错 → 整页白屏
- 服务器宕机 → 每个页面独立报错 → 用户看到 5 种不同的错误提示
- 多个请求同时 401 → 多次跳转登录页

### 根因 2：API 路由前缀不一致（基建问题）

- nginx 反代：`/api/*` → 去掉 `/api` 前缀转发到 `127.0.0.1:3000`
- 后端部分路由注册了 `/api/stats/fields`（带前缀）
- nginx 转发后变成 `/stats/fields`，后端找不到 → 404
- **影响**：字段统计、Dashboard 统计、趋势图 3 个 API 全部失效

### 根因 3：功能"有入口无闭环"（产品设计缺陷）

多个功能只做了"看"的部分，没做"改"的部分：

| 功能 | 能看 | 能改 | 闭环？ |
|------|------|------|--------|
| 反馈管理 | ✅ 列表查看 | ❌ 无法审核/批准/拒绝 | ❌ |
| Provider 管理 | ✅ 列表+健康检查 | ❌ 无法新建/编辑/删除 | ❌ |
| Schema 管理 | ✅ 列表+版本查看 | ❌ 无法新建/编辑字段 | ❌ |
| 评测中心 | ✅ 框架在 | ❌ 样本只能粘 JSON | ❌ |
| 回写管理 | ✅ 历史记录 | ❌ 手动触发不可用 | ❌ |
| 审计日志 | ✅ 列表查看 | ❌ 无筛选/导出 | ❌ |
| Dashboard | ✅ 4 个数字 | ❌ 无趋势图/快捷操作 | ❌ |

**这不叫"功能完成"，叫"功能半成品"**。用户打开一个页面，看到数据躺在那里，但什么都做不了——这不是产品，是 Demo。

## 三、问题清单（体验 + 功能合并）

### P0-A：全局错误处理缺失

| 现象 | 根因 | 产品影响 |
|------|------|---------|
| 5 个按钮点了没反应 | POST/DELETE 无 body → Fastify 400 → 静默 catch | 用户以为系统坏了，反复点击 |
| 页面白屏 | 无 React Error Boundary | 用户只能刷新，丢失操作状态 |
| 服务器宕机时各页面独立报错 | 无全局网络状态检测 | 用户看到 5 种不同错误提示 |
| API 错误是英文技术术语 | 未做错误信息翻译 | 用户看到 `FST_ERR_CTP_EMPTY_JSON_BODY` 一脸懵 |
| 401 多次跳转 | 无去重锁 | 多次跳转登录页，体验极差 |

**受影响的按钮**：

| 按钮 | 页面 | 当前行为 | 应有行为 |
|------|------|---------|---------|
| 停用 | Schema 详情 | 静默失败 | 按钮 loading → 成功 toast 刷新列表 / 失败 toast 含原因 |
| 回滚 | Schema 详情 | 静默失败 | 同上 |
| 删除 | 任务列表 | 静默失败 | 确认弹窗 → loading → 成功/失败反馈 |
| 重跑 | 任务列表 | 静默失败 | loading → 成功提示跳转新任务 |
| 触发回写 | 回写管理 | 静默失败 | 确认弹窗 → loading → 成功/失败反馈 |

### P0-B：API 路由 404（6 个路由失效）

| API | 用途 | 影响 |
|-----|------|------|
| `/api/stats/fields` | 字段识别详情统计 | Schema 详情页"字段统计"tab 无数据 |
| `/api/stats/dashboard` | 工作台统计数据 | Dashboard 统计卡片数据异常 |
| `/api/stats/trend` | 识别趋势图 | 趋势图无法渲染 |
| `/api/jobs/:id/export` | 任务结果导出 | "导出"按钮 404 |
| `POST /api/providers` | 创建 Provider | Provider 管理无法新建 |
| `PATCH /api/feedback/:id` | 审核反馈 | 反馈管理无法审核 |

### P0-C：登录状态不持久化

**现象**：刷新页面 → 跳回登录页 → 需重新登录

**根因**：`authStore.ts` 有 `restore()` 方法，但 `App.tsx` 从未调用。

**产品影响**：每次 F5 都要重新登录，用户会认为"这个系统很不稳定"。

### P1-A：反馈管理无闭环（功能缺失）

**现状**：
- 用户在 JobDetailPage 提交反馈（"这个字段值应该是 XX"）→ 写入 `FeedbackSubmission` 表
- 反馈管理页只能查看列表、筛选、导出
- **无法审核、批准、拒绝**
- 批准的反馈**不会写入知识库**，不影响后续识别

**产品视角**：这是一个只有"输入"没有"处理"的功能。用户提交了反馈，看到它躺在列表里，永远不会有人处理它。**等于没做。**

**完整闭环应该是**：
```
用户提交反馈 → 反馈管理页审核 → 批准 → 写入 KnowledgeEntry 表 → RAG 检索命中 → 后续识别更准
                ↓
              拒绝 → 标记原因 → 不影响知识库
```

**需要做的**：
1. 后端：`PATCH /api/feedback/:id/status` — 审核状态变更（待审核→批准/拒绝）
2. 后端：批准后自动写入 `KnowledgeEntry` 表（schemaKey + fieldName + sourceValue + targetValue）
3. 前端：审核操作按钮（批准/拒绝，带确认弹窗）
4. 前端：批量审核（勾选多条 → 批量批准/拒绝）
5. 前端：审核状态筛选（待审核 / 已批准 / 已拒绝 / 全部）
6. **闭环验证**：RAG 检索能否命中反馈修正的字段值

---

### P1-B：评测中心样本导入门槛高（功能缺失）

**现状**：只支持手动粘贴 JSON 数组

**产品视角**：评测中心的目标用户是**质量管理人员**和**业务人员**，不是开发人员。让他们粘贴 JSON 是反人类设计。他们手里有的是：已经识别过的结果、Excel 表格、纸质报告。

**应该支持的导入方式**：
1. **从已有识别结果导入**（最常用）：下拉选择任务 → 预览 → 一键导入为评测样本
2. **逐条表单录入**：字段名 + 期望值，不需要知道 JSON 格式
3. **CSV/Excel 上传**：表头对应字段名，每行一条样本
4. **批量编辑**：导入后可以在表格里直接修改期望值

---

### P1-C：Provider 管理不可写（功能缺失）

**现状**：只能查看 Provider 列表和健康状态，无法新建/编辑/删除

**产品视角**：用户看到 Provider 列表，想加一个新的 OCR Provider（比如切换到另一个 OCR 服务），发现没有"新建"按钮。想修改 API Key，发现没有"编辑"按钮。**这个页面只是个只读看板，不是管理工具。**

**需要做的**：
1. 新建 Provider 表单（选择类型 → 填写 endpoint / API Key → 测试连接 → 保存）
2. 编辑 Provider 配置（修改 endpoint、API Key、模型参数等）
3. 删除 Provider（带确认弹窗，检查是否有关联任务）
4. 设置默认 Provider（切换默认时自动取消旧默认）
5. 启用/禁用切换（禁用后新任务不使用该 Provider）
6. 健康检查保留（已有）

---

### P1-D：Schema 管理不可写（功能缺失）

**现状**：只能查看版本列表、停用、回滚，无法创建新 Schema 或编辑字段定义

**产品视角**：Schema 是系统的**核心配置**——它定义了"识别什么字段"。用户想加一个新的报告类型（比如"骨髓报告"），发现只能用预置的 Schema。想给现有 Schema 加一个新字段，发现没有编辑入口。**核心配置不能管理，等于系统不可定制。**

**需要做的**：
1. 新建 Schema（填写 key、名称、描述）
2. 字段编辑器（添加/删除/排序字段，设置类型、描述、是否必填、枚举值）
3. 发布新版本（草稿 → 验证字段完整性 → 发布 → 自动成为 active 版本）
4. 版本对比（两个版本的字段差异）
5. 停用/回滚保留（已有）

---

### P1-E：回写管理无法手动触发（功能缺失）

**现状**："可回写任务" tab 始终为空，无法手动触发回写

**产品视角**：回写是整个流程的**最后一步**——把识别结果推送到目标系统。现在这个页面有"历史记录" tab（能看过去回写过的），但核心的"触发回写"功能不可用。**收尾环节断了，前面的工作都白费。**

**需要做的**：
1. 展示已完成任务列表（可回写的候选）
2. 一键回写按钮
3. 回写前预览（将要推送哪些字段）
4. 回写失败后重试（已有部分逻辑）
5. 回写目标配置（目标系统 URL、认证信息）

---

### P2-A：任务列表缺分页和搜索（体验粗糙）

**现状**：请求 `?limit=200`，一次性加载全部任务，无搜索筛选

**产品视角**：当前 demo 数据少，问题不明显。但实际使用后，任务会越来越多，没有分页 = 找不到任务。没有搜索 = 要翻遍整个列表。

**需要做的**：
1. 后端分页（page + pageSize + total）
2. 前端分页组件
3. 搜索框（任务 ID / Schema 名）
4. 状态筛选（全部 / 排队中 / 运行中 / 已完成 / 失败）
5. 日期范围筛选

---

### P2-B：任务列表列数据缺失（体验粗糙）

| 列 | 现状 | 根因 | 修复方案 |
|----|------|------|---------|
| 文件名 | 全部 `-` | 前端未关联 StoredFile.originalName | 后端 JOIN 查询返回文件名 |
| 整体置信度 | 全部 `-` | 前端未从结果计算 | 后端计算平均置信度返回 |
| 需复核 | 全部 `-` | 前端未统计 | 后端统计 needs_review 字段数返回 |
| Provider | 全部 `-` | 创建时未记录 | 任务创建时记录使用的 Provider |
| 创建人 | 全部 `-` | API 创建无 userId | 区分 API 创建 vs 页面创建 |

**产品视角**：5 列数据全是 `-` 的表格，等于只有一列有用信息。这不是"数据缺失"，是"表格设计过度"——列了当时没有数据的字段。短期应隐藏无数据列，中期补全数据。

---

### P2-C：Dashboard 信息不足（体验粗糙）

**现状**：只有 4 个统计卡片（今日任务数、待复核、已完成、Provider 在线）

**产品视角**：工作台是用户每天打开的第一个页面。4 个数字卡片不够回答"最近情况怎么样"这个最基本的问题。

**需要做的**：
1. 最近 7 天识别趋势折线图（任务量 + 完成率）
2. 字段识别准确率 TOP10 / BOTTOM10
3. 常见失败原因 TOP5
4. 快捷操作入口（新建识别、查看待复核任务、查看最新反馈）
5. 最近活动时间线（最近 10 条操作）

---

### P2-D：审计日志只有只读（体验粗糙）

**现状**：只能查看操作日志列表，无筛选/导出

**需要做的**：
1. 时间范围筛选
2. 操作类型筛选（创建/更新/删除/审核等）
3. 操作人筛选
4. 导出 CSV
5. 关联对象跳转（点击日志可跳转到对应任务/Schema）

---

| 项目 | 现状 | 需求 |
|------|------|------|

## 四、技术债务

| 项目 | 现状 | 修复方案 | 优先级 |
|------|------|---------|--------|
| POST/DELETE 无 body | Fastify 400 | `request()` 自动补 `{}` + 后端 body optional | P0 |
| API 路由前缀不一致 | 部分带 `/api/` | 统一不带前缀 | P0 |
| 401 竞态 | 多请求同时 redirect | 加 401 去重锁 | P1 |
| 无 Token Refresh | 过期直接踢出 | 实现 refresh token 或静默续期 | P2 |
| API 启动依赖 .env | 手动启动易忘 | 统一用 start-api.sh | P1 |
| 置信度计算 | 老数据格式不兼容 | 后端统一计算 | P1 |
| 构建缓存 | 旧 JS 文件未清理 | 构建脚本增加清理 | P2 |

## 六、不做什么（明确排除）

1. **不做多租户**：当前单租户够用
2. **不做角色权限细化**：当前只有 admin，不需要 RBAC
3. **不做移动端 App**：响应式 Web 够用
4. **不做实时协作**：单人操作场景，不需要 WebSocket 推送
5. **不做 AI 自动标注**：当前人工复核流程足够
