## 二、根因分析

### 2.1 🔴 核心问题：Workflow 执行时间过长

**现象**：单样本需要 400-600 秒，远超合理范围。

**根因**：Workflow 阶段过多，每个阶段都调用 LLM：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| OCR/图片加载 | ~5s | 正常 |
| RAG 知识检索 | ~1s | 38条规则 |
| **提取 (extractFields)** | **60-120s** | volces-seed-2-pro，547KB请求体 |
| **视觉审查 (visualReview)** | **80-200s** | volces-kimi-k26，535KB请求体 |
| **冲突解决 (conflictResolution)** | ~1s | 检测到7个冲突(5高) |
| **验证 (validation)** | ~1s | 决策: blocked |
| **重提取 (re-extraction)** | **60-120s** | 冲突触发，再次调用LLM |
| **总计** | **200-440s** | 不含重试 |

**问题**：
1. 提取阶段请求体 547KB（含 base64 图片 + 22字段prompt + 38条知识库规则），LLM 处理慢
2. 视觉审查再次调用 LLM，又增加 80-200s
3. 冲突解决触发重提取，再加 60-120s
4. 如果任何阶段超时，重试从头开始

### 2.2 🔴 Schema 设计过于复杂

**V3 Schema 有 22 个字段**，但：
- 基线测试只覆盖 11 个字段
- 新增字段（metastasis, ihc, patientAge）没有基线值，无法评估
- 字段越多，LLM 提取越慢、越容易出错
- 冲突解决检测到 7 个冲突 → 触发重试 → 超时

**字段分层设计问题**：
```
必填 (7个): pathologicalDiagnosis, interpretationMatch, cancerTag, 
            cancerCategory, tumorType, hospitalName, patientName
强期望 (5个): patientGender, detectionItems, reportDate, 
              treatmentHistory, sampleType
选填 (10个): clinicalStage, surgery, medication, radiotherapy, 
             geneMutations, familyHistory, metastasis, ihc, 
             patientAge, notes
```

**问题**：
- 必填字段太多（7个），LLM 需要同时识别 7 个高精度字段
- cancerTag 和 cancerCategory 是衍生字段（从 pathologicalDiagnosis 推导），不应作为独立必填
- interpretationMatch 也是衍生字段，增加 LLM 负担

### 2.3 🟡 冲突解决策略过于激进

**现象**：每个样本检测到 7 个冲突（5 高），触发重提取。

**问题**：
- 冲突检测阈值可能太低
- 重提取不会改善结果（同样的 LLM、同样的输入）
- 重提取浪费 60-120 秒，导致超时

### 2.4 🟡 视觉审查 ROI 低

**现象**：视觉审查耗时 80-200 秒，但不改善提取准确率。

**问题**：
- 视觉审查只做"质量评估"，不修正提取结果
- 增加 1 个 LLM 调用，但对准确率无贡献
- 535KB 请求体，处理慢

### 2.5 🟡 cancerCategory 匹配规则不清晰

**现象**：TC007 和 TC008 都错在 cancerCategory（输出'消化道肿瘤'，期望更精确分类）。

**问题**：
- 知识库中 cancerCategory 的分类规则不够精确
- LLM 倾向于输出大类（如"消化道肿瘤"），而非精确分类（如"食管鳞状细胞癌"）

## 三、架构设计缺陷

### 3.1 过度工程化

```
当前流程：OCR → RAG → 提取 → 视觉审查 → 冲突解决 → 重提取 → 验证 → 输出
理想流程：OCR → 提取 → 输出
```

- 视觉审查、冲突解决、重提取 三个阶段增加了 200-400 秒，但不提升准确率
- 对于病历识别这种"单图单次提取"场景，简单直接的流程更高效

### 3.2 请求体过大

- 提取请求：547KB（含 base64 图片 + prompt + 知识库）
- 视觉审查请求：535KB
- Node.js 内置 fetch 在 >200KB 时有概率性挂起（已用 undici 修复，但仍是风险点）

### 3.3 超时机制不合理

- LLM 超时 300s（后改 600s）太长
- 测试超时 600s 仍不够
- 应该在阶段级别设置超时，而非整体超时

## 四、改进方案

### 方案 A：精简流程（推荐）

**目标**：单样本 < 60 秒，准确率 > 90%

**改动**：
1. **关闭视觉审查**：`enableVisualReview: false`
2. **关闭冲突解决重试**：`maxRetryRounds: 0`
3. **精简 Schema 到 11 个字段**（只保留基线覆盖的字段）：
   ```
   必填 (4个): pathologicalDiagnosis, interpretationMatch, cancerTag, cancerCategory
   选填 (7个): surgery, clinicalStage, medication, radiotherapy, 
               sampleType, geneMutations, familyHistory
   ```
4. **移除衍生字段**：tumorType（= interpretationMatch）、hospitalName、patientName 等
5. **优化 prompt**：减少知识库规则到 10 条核心规则

**预期效果**：
- 请求体从 547KB 降到 ~200KB
- 单次 LLM 调用，60-120 秒完成
- 无重试，无视觉审查
- 总耗时 < 120 秒/样本

### 方案 B：优化当前流程

**改动**：
1. 保持视觉审查，但设置阶段超时（视觉审查最多 120s）
2. 冲突解决只重试高置信度冲突（而非所有高冲突）
3. 精简 Schema 到 15 个字段
4. 增加测试超时到 1200s

**预期效果**：
- 单样本 200-300 秒
- 准确率 80-90%

### 方案 C：分阶段测试

**改动**：
1. 先测"提取准确率"（关闭视觉审查、冲突解决）
2. 再测"视觉审查增益"
3. 最后测"冲突解决增益"

**目的**：量化每个阶段的 ROI，决定取舍

## 七、总结

**核心问题**：系统设计过度工程化，22字段 Schema + 视觉审查 + 冲突重试 导致单样本处理时间过长（400-600秒），无法在合理时间内完成 45 样本测试。

**根本原因**：
1. Schema 字段太多（22个 vs 实际需要11个）
2. Workflow 阶段太多（提取+视觉审查+冲突解决+重提取）
3. 请求体太大（547KB）
4. 超时设置不合理

**建议**：先做减法（精简 Schema + 关闭视觉审查），把基础准确率做到 90%+，再逐步增加功能。

## 八、架构优化实施记录（2026-06-22）

基于本报告分析，已实施 5 项架构优化，采用"重构拓扑而非删功能"的思路，保留多文档视觉审查和 OCR 兜底能力。

### 8.1 已完成优化

| 任务 | 改动 | 效果 |
|------|------|------|
| **任务1 阶段超时** | 接线 `VisualReviewConfig.timeoutMs`(此前死配置),用 `Promise.race` 包装 extractFields,超时走 degraded 降级 | 视觉审查不再无限挂起,超时后降级继续(不阻塞流程) |
| **任务3 提取模式开关** | SupervisorDecision 新增 `extractionMode: single\|multiSource`;单图默认 single(1次LLM调用),多文档切 multiSource(完整拓扑) | 单图样本跳过视觉审查+重试,预期耗时压到 60-120s |
| **任务2 统一测试体系** | evaluate.py schemaKey 对齐 baseline.json;新建 roi_test.py 三模式对比脚本 | 消除两套测试体系不互通问题,可量化各阶段 ROI |
| **任务5 冲突解决重构** | 子串包含不算冲突(值相近);high 阈值 0.6→0.7;真矛盾才重试 | 消除同模型采样噪声导致的伪冲突重试 |
| **任务4 Schema 确认** | core schema 12 字段已精简,无 V3 的衍生字段冗余,与 baseline 完全对齐 | 无需改动,确认分层合理 |

### 8.2 关键设计决策

- **不删节点,按模式启用**:visualReview/conflictResolution 节点保留,single 模式跳过,multiSource 模式完整可用。多文档视觉审查(P0-1)和 OCR 兜底(P0-2)能力不回退。
- **providerConfig 覆盖**:单任务可通过 `providerConfig.extractionMode/enableVisualReview/maxRetryRounds` 覆盖 supervisor 决策,供 ROI 测试按模式控制。
- **冲突解决从"双源裁决"改为"置信度门控"**:提取和视觉审查输入高度重叠,冲突多为噪声;子串包含(值相近)不算冲突,真矛盾且高置信才重试。

### 8.3 ROI 量化测试方法

```bash
# 三种模式对比(默认跑 P0 优先级样本)
python scripts/roi_test.py --mode all --filter-priority P0

# 单模式测试
python scripts/roi_test.py --mode extract_only --filter-priority P0
python scripts/roi_test.py --mode extract_visual --filter-priority P0
python scripts/roi_test.py --mode full --filter-priority P0
```

输出:完成数/平均耗时/准确率/字段级准确率的多模式对比表。**预期**:extract_only 模式单样本 < 120s,full 模式仍 400-600s(但 single 模式已成为默认,单图样本不再走完整流程)。
