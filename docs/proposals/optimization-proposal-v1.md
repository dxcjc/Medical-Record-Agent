## 四、P1：多轮抽取方案

### 4.1 设计思路

**核心思想**：第一轮抽取后，针对缺失字段做第二轮定向抽取。

### 4.2 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    多轮抽取引擎                          │
├─────────────────────────────────────────────────────────┤
│  第一轮：全字段抽取                                       │
│  ├─ 输入：OCR文本 + 知识库                               │
│  └─ 输出：结构化JSON（可能有缺失字段）                    │
│                                                         │
│  缺失字段检测                                            │
│  ├─ 分析confidence=0的字段                               │
│  └─ 生成第二轮抽取prompt                                 │
│                                                         │
│  第二轮：定向抽取                                        │
│  ├─ 输入：原始OCR + 缺失字段列表                         │
│  └─ 输出：补充字段JSON                                   │
│                                                         │
│  结果合并                                                │
│  ├─ 合并两轮结果                                         │
│  └─ 冲突处理（优先第二轮）                               │
└─────────────────────────────────────────────────────────┘
```

### 4.3 实现细节

#### 4.3.1 缺失字段检测

```typescript
interface ExtractionResult {
  fields: Record<string, {
    value: string;
    confidence: number;
    source: 'ocr' | 'llm' | 'visual';
  }>;
}

function detectMissingFields(result: ExtractionResult): string[] {
  const requiredFields = ['cancerType', 'gender', 'hospital', 'sampleType'];
  return requiredFields.filter(field => 
    !result.fields[field]?.value || 
    result.fields[field].confidence < 0.3
  );
}
```

#### 4.3.2 第二轮Prompt生成

```typescript
function generateSecondRoundPrompt(
  ocrText: string, 
  missingFields: string[]
): string {
  return `
基于以下OCR文本，重点提取以下缺失字段：
${missingFields.join(', ')}

OCR文本：
${ocrText}

请以JSON格式返回结果，只包含上述字段。
`;
}
```

#### 4.3.3 结果合并策略

```typescript
function mergeResults(
  firstRound: ExtractionResult,
  secondRound: ExtractionResult
): ExtractionResult {
  const merged = { ...firstRound };
  
  for (const [field, value] of Object.entries(secondRound.fields)) {
    // 如果第二轮有更高置信度的结果，使用第二轮
    if (value.confidence > (merged.fields[field]?.confidence || 0)) {
      merged.fields[field] = value;
    }
  }
  
  return merged;
}
```

## 五、P2：视觉评审增强方案

### 5.1 当前视觉评审

- 模型：kimi-k2.6（视觉能力）
- 功能：识别12个字段，用于验证抽取结果
- 问题：只用于验证，未充分利用

### 5.2 增强策略

#### 5.2.1 视觉结果作为候选字段

**当前流程**：
```
OCR → LLM抽取 → 视觉评审（仅验证）
```

**优化流程**：
```
OCR → LLM抽取 → 视觉评审（验证+补充）
                 ↓
                 视觉结果作为候选字段
                 ↓
                 合并到最终结果
```

#### 5.2.2 实现细节

```typescript
interface VisualReviewResult {
  fields: Record<string, {
    value: string;
    confidence: number;
    source: 'visual';
  }>;
  validation: {
    issues: string[];
    suggestions: string[];
  };
}

function mergeVisualResults(
  extractionResult: ExtractionResult,
  visualResult: VisualReviewResult
): ExtractionResult {
  const merged = { ...extractionResult };
  
  for (const [field, value] of Object.entries(visualResult.fields)) {
    // 如果视觉结果置信度更高，使用视觉结果
    if (value.confidence > (merged.fields[field]?.confidence || 0)) {
      merged.fields[field] = {
        ...value,
        source: 'visual'
      };
    }
  }
  
  return merged;
}
```

#### 5.2.3 针对特定字段的视觉优先

**视觉优先字段**：
- 勾选框（如性别、样本类型）
- 手写体（如签名、日期）
- 表格结构（如检测结果）

**实现方式**：
- 在视觉评审prompt中增加对这些字段的重点识别
- 设置视觉结果的置信度权重更高

### 5.3 资源需求

| 项目 | 工作量 | 影响 |
|------|--------|------|
| 视觉结果合并逻辑 | 3小时 | 代码修改 |
| 视觉评审prompt优化 | 2小时 | Prompt工程 |
| 字段优先级配置 | 1小时 | 配置文件 |

## 六、P3：OCR升级方案（备选）

### 6.1 当前OCR状态

| 项目 | 值 |
|------|-----|
| 版本 | PaddleOCR 3.0.0 |
| 模型 | mobile（轻量级） |
| 内存占用 | 417MB |
| 状态 | 运行正常 |

### 6.2 升级选项

#### 选项A：升级到PaddleOCR 3.1/4.0

**优点**：
- 可能有更高的识别准确率
- 支持更多语言和场景

**缺点**：
- 需要更多内存（可能需要600MB+）
- 磁盘空间不足（仅剩3.9GB）
- 需要重新部署

**资源需求**：
- 内存：+200MB（总计600MB+）
- 磁盘：+500MB（模型文件）
- 部署时间：2-4小时

**风险评估**：
- 🔴 **高风险**：磁盘空间不足，可能导致服务不稳定
- ⚠️ **中风险**：内存紧张，可能影响其他服务

#### 选项B：使用server模型替代mobile模型

**优点**：
- server模型准确率更高
- 对复杂排版、手写体识别更好

**缺点**：
- 内存占用更大（可能需要800MB+）
- 推理速度更慢

**资源需求**：
- 内存：+400MB（总计800MB+）
- 磁盘：+1GB（模型文件）
- 部署时间：2-4小时

**风险评估**：
- 🔴 **高风险**：资源严重不足
- 🔴 **高风险**：可能导致OOM（内存溢出）

#### 选项C：使用云OCR服务

**优点**：
- 无本地资源消耗
- 通常有更高的准确率
- 支持更多场景

**缺点**：
- 需要网络调用，增加延迟
- 有API调用成本
- 数据安全考虑

**资源需求**：
- 本地资源：0
- 网络带宽：+3M（可能影响其他服务）
- 成本：按调用次数计费

**风险评估**：
- ⚠️ **中风险**：网络延迟可能影响用户体验
- ⚠️ **中风险**：API成本可能较高

### 6.3 推荐方案

**结论**：在当前服务器资源下，**不建议升级OCR**。

**原因**：
1. **磁盘空间严重不足**：仅剩3.9GB，无法部署更大模型
2. **内存紧张**：已用1.9GB，可用1.7GB，无法承载更重模型
3. **成本效益比低**：升级带来的收益（可能+5-10%准确率）不值得承担的风险

**建议**：
- 保持当前PaddleOCR 3.0.0 mobile模型
- 通过知识库增强和多轮抽取弥补OCR的不足
- 如果未来服务器资源充足，再考虑升级

## 十、结论与建议

### 10.1 核心结论

1. **知识库增强**是当前最有效、最低风险的优化手段
2. **多轮抽取**能显著提升准确率，但会增加API调用成本
3. **视觉评审增强**能进一步提升准确率，但收益递减
4. **OCR升级**在当前资源下不建议，风险过高

### 10.2 最终建议

**推荐方案**：P0 + P1 + P2（知识库增强 + 多轮抽取 + 视觉评审增强）

**预期效果**：
- 准确率：60% → **90%+**
- 开发周期：**6天**
- 月增成本：**¥500**

**不推荐**：P3（OCR升级）

**原因**：
- 资源限制：磁盘空间不足，内存紧张
- 风险过高：可能导致服务不稳定
- 收益有限：准确率提升仅5-10%
