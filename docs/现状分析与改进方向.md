## 一、当前架构状态

### 1.1 目录结构（清理后）

```
Medical-Record-Agent/
├── apps/
│   ├── api/              # Fastify 后端 (20+ 路由)
│   ├── web/              # React 前端 (10 个页面, Arco Design)
│   └── cli/              # CLI 工具
├── packages/
│   ├── core/             # 核心逻辑 (workflow/Agent/校验/知识库)
│   └── shared/           # 共享类型
├── scripts/              # 测试/运维脚本
├── test-data/            # 45 样本测试集
├── docs/                 # 文档
├── prisma/               # 数据库 schema
└── e2e/                  # Playwright E2E 测试
```

### 1.2 Workflow 拓扑（当前）

```
START → supervisor → ocr → rag → extraction → visualReview
  → conflictResolution → validation
      ├─ 重试(3种触发条件,最多2轮) → extraction
      └─ 通过 → autoDecision → writeback → evaluation → END
```

- **12 个节点**，1 条条件边，3 种重试触发条件
- **single 模式**（默认）：跳过 visualReview + conflictResolution + 重试，1 次 LLM 调用
- **multiSource 模式**（多文档）：完整 8 阶段拓扑，支持视觉审查交叉验证
- 已实施：阶段超时 + 降级、冲突解决重构、extractionMode 开关

### 1.3 Schema 体系

| Schema | 字段数 | 场景 |
|--------|--------|------|
| medical-record-core | 12 | 通用病历识别（当前主力） |
| V3 (仅DB) | 22 | 含衍生字段，已诊断废弃 |
| lims-clinical-info | 10 | LIMS 写回 |

## 二、Agent 能力现状与缺口

### 2.1 ✅ 已具备的能力

| 能力 | 说明 | 状态 |
|------|------|------|
| OCR → 结构化抽取 | 基础链路完整 | ✅ 稳定 |
| RAG 知识检索 | L1 保证注入 + L2 评分排序 top-15 | ✅ |
| 多文档视觉审查 | P0-1: 多图交叉验证 | ✅ |
| OCR 漏识兜底 | P0-2: 关键区域空文本触发视觉审查 | ✅ |
| 字段后处理 | pathologicalDiagnosis 简化 + clinicalStage 标准化 | ✅ |
| 冲突解决 | 子串不算冲突 + 阈值 0.7 | ✅ |
| 反馈循环重试 | 聚焦字段重抽，最多 2 轮 | ✅ |
| 提取模式切换 | single(默认) / multiSource | ✅ |
| 阶段超时 | visualReview 90s 超时降级 | ✅ |
| 知识库 | in-memory 50 条 + seed 74 条 | ✅ |

### 2.2 ❌ 缺失/薄弱的能力

| 缺口 | 严重度 | 说明 |
|------|--------|------|
| **无跨字段一致性校验** | 🔴 | validationEngine 只做单字段校验，不检查 tumorType 与 tumorCategory 是否一致、patientGender 与 idNumber 性别位是否匹配 |
| **无语义检索** | 🔴 | L2 检索靠 OCR 文本关键词包含匹配，OCR 识别错误会导致检索完全失效。应升级为向量检索 |
| **in-memory 知识库落后于 seed** | 🟡 | memory 版 50 条 vs seed 74 条，缺少 cancer_category/sample_type_mapping/gender_inference 等 4 个 kind，内存版测试与生产行为不一致 |
| **提取阶段无超时** | 🟡 | 只对 visualReview 有阶段超时，extraction 靠 provider 层超时(http 模式有，langchain/responses 无) |
| **重试调用同模型** | 🟡 | 重试用同一 LLM、同一 prompt，改善有限。应支持重试时换模型或换 prompt 策略 |
| **无局部重试** | 🟡 | OCR 失败直接 blocked，无重试机制。应支持 OCR 重试 1-2 次后再失败 |
| **无字段间逻辑约束** | 🟢 | 如"pathologicalDiagnosis 为空则 blocked"的逻辑不在 validationEngine 层 |
| **无日期/数值范围校验** | 🟢 | date 类型字段不校验日期合法性，数值字段不校验范围 |

### 3.3 用户操作链路痛点

**核心链路：上传 → 识别 → 看结果（3 页面 / 6 步）**
- 上传页无"常用 Schema"推荐或最近使用
- 任务列表无批量操作（只能逐条删除）
- 任务详情页信息密集（字段分组+置信度+OCR+证据+Trace），新用户容易困惑

**辅助链路：发现问题 → 反馈 → 审核 → 回写**
- 反馈 Drawer 无预填建议值（虽然有 RuleCandidate 但未集成到反馈流程）
- 回写页面无批量回写
- 审核/回写状态变更后页面不自动刷新

## 四、核心问题总结（按优先级）

### 🔴 P0 — 必须改进

| # | 问题 | 分类 | 影响 |
|---|------|------|------|
| 1 | **无语义检索** — L2 知识检索靠 OCR 关键词包含匹配，OCR 识别错就全丢 | Agent 能力 | 知识库 74 条规则在 OCR 质量差时全部失效 |
| 2 | **in-memory 与 seed 知识库不一致** — 内存版 50 条 vs seed 74 条，缺 4 个 kind | Agent 能力 | 测试用内存版，生产用 seed，行为不一致 |
| 3 | **无跨字段一致性校验** — validationEngine 只做单字段校验 | Agent 能力 | 如 tumorType 和 tumorCategory 给出矛盾值时无法发现 |
| 4 | **首屏加载所有页面 JS** — 无 React.lazy/Suspense | 前端性能 | 首页加载 ~1.1MB JS（vendor + 所有页面） |

### 🟡 P1 — 应该改进

| # | 问题 | 分类 | 影响 |
|---|------|------|------|
| 5 | **提取阶段无超时** — 只 visualReview 有阶段超时 | Agent 能力 | extraction 走 langchain/responses provider 时可能无限挂起 |
| 6 | **OCR 失败无重试** — 直接 blocked | Agent 能力 | 瞬时 OCR 故障导致整个任务失败 |
| 7 | **重试用同模型** — 改善有限 | Agent 能力 | 应支持重试时换模型/换 prompt 策略 |
| 8 | **表单校验不一致** — 部分无字段级高亮 | 前端体验 | 用户提交后才知道错在哪 |
| 9 | **快捷跳转不足** — 评测中心/反馈入口缺失 | 前端体验 | 用户需要在页面间反复切换 |
| 10 | **空状态引导不足** — Evaluation/Feedback/Audit 页 | 前端体验 | 新用户不知道下一步做什么 |

## 五、建议的改进方向

### 5.1 Agent 能力（短期）

1. **同步 in-memory 与 seed 知识库**：补齐 memory 版缺失的 4 个 kind，使测试与生产行为一致
2. **提取阶段超时**：给 extractionNodeAction 加与 visualReview 相同的 `withTimeout` 包装
3. **OCR 重试**：ocrNode catch 中加 1 次重试后再 blocked

### 5.2 Agent 能力（中期）

4. **语义检索升级**：用 embedding + 向量检索替代关键词包含匹配，消除 OCR 质量依赖
5. **跨字段一致性校验**：validationEngine 新增跨字段规则（如 tumorType↔tumorCategory、gender↔idNumber）
6. **重试策略多样化**：支持重试时换模型或换 prompt 模板

### 5.3 前端友好度（短期）

7. **React.lazy 代码分割**：10 个页面全部改为按需加载，首屏减重 ~60%
8. **统一表单校验**：NewRecognitionPage/LoginPage/FeedbackDrawer 改用 Arco Form rules 实现字段级错误高亮
9. **补全快捷跳转**：JobListPage/ProviderPage/DashboardPage 加评测中心入口

### 5.4 前端友好度（中期）

10. **批量操作**：任务列表加批量删除、回写页面加批量回写
11. **Schema Drawer 分组**：字段按业务分组展示（患者信息/样本信息/检测信息）
12. **全局搜索**：搜索栏可搜任务/Schema/Provider
